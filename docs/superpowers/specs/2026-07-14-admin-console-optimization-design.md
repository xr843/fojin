# 管理后台优化设计 — 差答案队列降噪 + 菜单重排

- 日期:2026-07-14
- 状态:已确认,待实施

## 背景:后台的真实状态

管理员反映后台"内容太多",日常只用「数据概览」和「用户管理」。实测生产后台(2026-07-14)后发现,问题不是菜单项多,而是**8 项里只有 2 个地方真有活儿,而这 2 个都没被用起来——其中 1 个甚至没有菜单入口**。

| 页面 | 待处理量 | 备注 |
|---|---|---|
| 差答案队列 | **715** | 从未复核过一条 |
| 候选对齐复核 | **50** | **不在菜单里**,只能从覆盖率页点进去;接受即写入生产语料 |
| 源建议 | 0 | 4 条历史全已采纳(最新 5/2) |
| 用户反馈 | 0 | 4 条历史全已解决(最新 4/13) |
| 标注审核 | 0 | 3 条历史 |
| 审计日志 | 0 | 空表 |

两个有积压的队列没人用,四个空队列却常驻菜单。

### 为什么差答案队列没人用

715 条里首页全是 `no_citation` 标签、可疑度一律 2.0,其中包括 `what can you do today?`、`请转换成 markdown 模式,我好直接复制给AI`、`本章有哪些公案` 这类**根本不需要引经**的问题。

根因:`no_citation` 的判据是"这条回答没有任何检索来源",它把两种完全不同的东西混为一谈——

- **噪音**:闲聊 / 元问题,本来就不该有来源
- **信号**:用户问了一部经,但语料库里没有(真实的覆盖缺口)

只看"有没有来源"永远分不开这两者。信号被噪音淹没,所以队列被无视。

### 一个让问题难以发现的 bug

`AdminAnswerQualityPage.tsx` 把队列和统计两个请求包在同一个 `Promise.all` 里,任一失败即走 `.catch()`,只弹一个 toast,而 `total` 保持初始值 `0`,表格渲染成「队列已清空」。**请求失败与队列真空在 UI 上完全同形。**(本次调查中,首次通过菜单进入该页时正是在加载中被误读为"队列是空的"。)

## 判据变更:从「有没有引经」改为「引用是否可核对」

### 决策

差答案队列只收录**引用不可核对**的回答,不再收录"没有来源"的回答。闲聊 / 元问题因为不做经文断言,自动出局。

这直接对准 fojin 的核心承诺(可核对引用),也正对着已知的逐字引用保真度缺口(38.1%,见 `fojin-quote-extractor-bug`)。不需要发明任何新的判断器(如"这个问题需不需要引经"的分类器),因为所需信号已经存在。

### 数据源

`chat_answer_diagnostics` 表(migration `0165`,2026-07-01 落地),按 `message_id` join。它记录了**入库前那一刻**的真相:

- `citation_count` — 回答做出了几处引用
- `source_count` — 检索到几条来源
- `quote_mutation_count` — 有几处"转述当原文引"被降级
- `citation_mutation_count` — 有几处引用被系统纠正
- `trust_state`、`max_source_score` / `min_source_score`

### 为什么必须用这张表,而不能对历史消息重算

`verify_quoted_content` 的契约是**"fojin 从不 *端出* 假的逐字引用"**(`quote_verifier.py:373-382`):对不上原文的引号会被**剥掉**,答案降级为模型自己的叙述,然后才入库(`chat.py:566` 重新赋值 `answer`,`_save_messages` 存的是纠正后的版本)。

**坏引用的证据在保存时就被销毁了。**对 `chat_messages.content` 重跑校验只会得到"一切正常"。唯一幸存的痕迹是 `chat_answer_diagnostics` 里的 mutation 计数。

**代价**:2026-07-01 之前的历史消息没有诊断行,**无法追溯**。队列窗口默认从 90 天收窄到 30 天,页面注明"引用可核对性检测自 2026-07-01 起"。

**这个代价可以接受**:诊断表覆盖期内(近 14 天)有 283 条候选,近 7 天 119 条,约每天 17 条新增——队列不会枯竭。

### 新的标签集与权重

| 标签 | 触发条件 | 权重 |
|---|---|---|
| `downvoted` | 用户点踩 | 5.0 |
| `fabricated_citation` | `citation_count > 0` 且 `source_count == 0`(引了经却零来源,凭空引用) | 4.0 |
| `quote_relaxed` | `quote_mutation_count > 0`(转述当原文引,被系统降级) | 3.0 |
| `citation_corrected` | `citation_mutation_count > 0`(引用被系统悄悄纠正) | 2.0 |
| `abnormal` | 回答少于 20 字 | 3.0 |
| `weak_evidence` | `max_source_score` 低于阈值 | 1.0 + 梯度 |
| ~~`no_citation`~~ | ~~无任何来源~~ | **删除** |

**删掉 `no_citation` 后,"语料覆盖缺口"这个信号去哪了?** 分两种情况,都不需要它:

- AI 因为检索不到而**凭空编造引用** → `fabricated_citation` 会抓到(而且这才是真正该管的:它伤害的是可核对性)
- AI 如实回答"语料库中没有这部经" → 这不是差答案,不该进复核队列。语料覆盖缺口应由**数据源侧的报表**回答,而不是靠差答案队列侧面反映。

`downvoted` 保留且今后真的会有数据:点踩曾因前端 PUT 到流式期间的 `Date.now()` 占位 id 而从未落库,**该 bug 已修**——后端现在会 `yield` 真实 `message_id`(`chat.py:1126-1139`),前端在拿到真 id 前隐藏点踩按钮(`ChatPage.tsx:495`)。代码注释里的 "has been zero" 是过去时。

### 阈值不拍脑袋定

`WEAK_EVIDENCE_THRESHOLD` 现为 `0.37`(2026-06-30 按当时 p10≈0.366 校准)。生产实测当前分布已是 **p10=0.31 / p50=0.595 / p90=0.874**——阈值偏高,正在误报。

**不在本次直接改数值。**先上线新判据,并让队列响应把**标签分布**一并吐出(照现有 `score_distribution` 的样子),看真实分布再定阈值。

## 性能:顺手修掉的全表扫

现在 `build_bad_answer_queue` 把窗口内**每一条** assistant 消息连同完整 `sources` JSON 全量拉进 Python,再在内存里分页(`answer_quality.py:182-192`、`:225`)。实测 1.8 秒 / 80KB,且随流量线性劣化,有 OOM 风险。

新判据的所有条件都是 `chat_answer_diagnostics` 上的**列比较**,可以直接用 SQL 表达。因此:

- `LIMIT` / `OFFSET` **下推到 SQL**
- 角标计数走一条便宜的 `COUNT(*)`,**不跑 Python 打分**

这是换判据白捡的好处。角标必须便宜——它会在每次导航时被读取。

## 菜单重排

菜单硬编码在 `frontend/src/components/Layout.tsx:100-109`;角标 `pendingCount` 在 `:61-69`(现只统计"待审源建议 + 待处理反馈",漏了标注,更漏了两个真有积压的队列)。

**常驻 4 项:**

1. **数据概览** → `/admin`
2. **用户管理** → `/admin/users`(页面右上角挂「审计日志」链接)
3. **差答案队列** `[角标]` → `/admin/answer-quality`
4. **跨藏对齐** `[角标]` → `/admin/alignment`,页面内两个 tab:**覆盖率**(决定下一部投哪经)+ **候选复核**(50 条)。`/admin/alignment/review` 保留为 tab 深链——那个隐藏页从此有门牌。

**第 5 项「待办」:** 子菜单为 源建议 / 用户反馈 / 标注审核,**角标为 0 时整项不渲染**。这三者都是被动响应型队列,没人提交就不该占视线。当前三者均为 0,故管理员平时只看到 4 项。

**审计日志**:移出菜单,路由保留。它当前既无数据,又漏审了最危险的写操作(见下)。

## 错误态(必修)

队列页请求失败时必须显示**错误态**,不得渲染成「未复核 0 条 / 队列已清空」。当前二者同形,是本次问题长期未被发现的直接原因。

## 明确不做(留独立 PR)

- **审计覆盖补全**。`record_audit()` 只在 3 处被调用(`admin.py:159` 改用户、`source_suggestions.py:150` / `:116` 源建议)。**未被审计**的写操作包括:标注审批、反馈回复、差答案裁决,以及 **对齐候选 accept —— 后台唯一会直接改写生产语料 `alignment_pairs` 的操作,却零审计记录**(`alignment_review.py:77-90`)。这是真问题,但与本次改造正交。

- **飞轮上游**:`mine_candidates` / `mine_from_anchors` 没有 CLI、没有 HTTP 入口、没进 cron,只能手工跑 python heredoc(`docs/alignment-prod-activation.md:236`)。50 条候选耗尽后需要人工再挖。
